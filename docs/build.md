# Building and publishing the test case

This page is for contributors. It describes the `dev` branch, which holds everything
needed to produce the test case, and how the `main` branch is published from it. Users
need only `main`: see [test-case.md](test-case.md).

## Branches

| Branch | Content                                                                                   | Edited                                          |
|--------|-------------------------------------------------------------------------------------------|-------------------------------------------------|
| `dev`  | Source models, hand-edited inputs, build code, generated `testcase/`, all documentation   | By hand, through `feature/*` and `fix/*` branches |
| `main` | `testcase/`, user documentation, presentation notebook and its Binder configuration       | Never: generated by `hynet-testcase publish`     |

`main` has a history of its own; the two branches are never merged. Each commit of
`main` names the `dev` commit it was published from, and its Binder installs the
package from that commit, so the history of `dev` must never be rewritten. Releases
are tagged on `main`.

The files of `main` that differ from `dev` are generated from `publish/`: its README
and the Binder `postBuild`. Relative links to files that are not published, such as
[model-changes.md](model-changes.md) or this page, point to `dev` at the published
commit.

## Rebuilding

The project uses [uv](https://docs.astral.sh/uv/) and Python 3.14. `testcase/` is
generated from `data/` and must not be edited by hand:

```sh
uv sync
uv run hynet-testcase build
```

## Presentation notebook

The notebook is committed with its outputs. To re-execute it:

```sh
uv run python -m nbconvert --to notebook --execute --inplace --ExecutePreprocessor.store_widget_state=False notebooks/presentation.ipynb
```

`store_widget_state=False` keeps the explorer's state (about 12 MB) out of the file.

Binder is configured in `binder/`: Python 3.14 (`runtime.txt`) and dependencies pinned
from `uv.lock` (`requirements.txt`). On `dev`, `postBuild` installs the package from
the repository in editable mode
([Binder on dev](https://mybinder.org/v2/gh/SuperGrid-Institute/hynet-t32-reference-test-case/dev?labpath=notebooks%2Fpresentation.ipynb)).
On `main`, which has no `src/`, it installs the package from the archive of the `dev`
commit `main` was published from; the notebook finds `testcase/` from its working
directory.

## Dependencies

Dependencies are managed with uv. After changing them, refresh both exported
requirement files:

```sh
uv export --format requirements-txt --no-dev --group notebooks --no-hashes -o requirements.txt
uv export --format requirements-txt --no-dev --group notebooks --no-hashes --no-emit-project -o binder/requirements.txt
```

## Publishing `main`

`main` is checked out in a separate worktree, next to the repository:

```sh
git worktree add --orphan -b main ../hynet-t32-main   # first publication only
git worktree add ../hynet-t32-main main               # once main exists on GitHub
```

Each publication starts from a clean `dev`, pushed first so that Binder on `main` can
install the package from it:

```sh
git push origin dev
uv run hynet-testcase publish ../hynet-t32-main
cd ../hynet-t32-main
git add --all
git update-index --chmod=+x binder/postBuild
git commit -m "chore(testcase): publish from dev@<commit>"
git push origin main
```

`publish` replaces everything in the worktree but `.git`. It stops if the working tree
is not a clean checkout of `dev`, if the target is not a separate git worktree, or if a
published path or link does not resolve, and warns if the `dev` commit is not pushed.
`git update-index` records the executable bit of `postBuild`, which Windows checkouts
do not.

## Inputs (`data/inputs/`)

Hand-edited files from which the build produces `testcase/`. The shipped files they
refer to are described in [data-dictionary.md](data-dictionary.md).

### `scenarios/`

| File                       | Shipped as                 | Schema                                                |
|----------------------------|----------------------------|-------------------------------------------------------|
| `generation_scenarios.csv` | `generation.csv`           | `timestamp, scenario, generator_id, p_mw`             |
| `load_scenarios.csv`       | `loads.csv`                | `timestamp, scenario, load_id, p_mw, q_mvar`          |
| `hvdc_setpoints.csv`       | `hvdc.csv`                 | `timestamp, scenario, hvdc_line_id, target_p_mw`      |
| `battery_setpoints.csv`    | `battery_setpoints.csv`    | `timestamp, scenario, battery_id, target_p_mw`        |
| `generators_metadata.csv`  | `generators.csv`           | as `generators.csv`                                   |

`scenario` holds the scenario name (`baseline`, `high_res_low_demand`,
`low_res_high_demand`). Each scenario has a single timestamp, the same in every file,
and sets every generator, load, HVDC line and battery of the network exactly once. The
build stops if a scheduled generator output lies outside the generator's active power
range (`min_p`, `max_p` of the network model).

### `zones/<variant>_bus_zones.csv`

Zone of every bus-breaker bus, with the same columns as the shipped `bus_zones.csv`.
The build stops if a bus is missing, unknown or listed twice, or if a zone is not
connected through its own branches.

### `storage/<variant>_batteries.csv`

Same columns as the shipped `batteries.csv`, without `zone_id`, which the build derives
from the zone mapping. The build adds each battery to the network models at its bus.
The build stops if a bus is unknown, an id is repeated or already used, power or
energy is not positive, an efficiency is outside (0, 1] or a state of charge outside
[0, 1].

### `economics/economics.yaml`

Shared by every variant: the parameters of `parameters.csv` except
`capital_recovery_factor`, which the build derives. Every key is required and every
value must be positive.

### `contingencies/<variant>_contingencies.csv`

Same columns as the shipped `contingencies.csv`. The build stops if an id or element is
repeated, an element is unknown or of another type, or a branch outage disconnects any
bus.

### `network/<variant>_thermal_limits.csv`

Permanent current limit of every line and two-winding transformer of the variant,
applied to both sides. The build stops if a branch is missing or unknown.

| Column              | Type   | Unit | Description                          |
|---------------------|--------|------|--------------------------------------|
| `branch_id`         | text   | —    | IIDM line or transformer id          |
| `permanent_limit_a` | number | A    | Permanent current limit              |
| `basis`             | text   | —    | Origin of the value                  |

### `network/<variant>_generator_data.csv`

Optional. Ratings, operating ranges and voltage control of every generator of the
source model, aligned with a reference model. A blank cell keeps the source value. The
build stops if a generator is missing, unknown or listed twice, if only one reactive
limit is given, or if a minimum is above its maximum.

| Column                 | Type    | Unit | Description                                             |
|------------------------|---------|------|---------------------------------------------------------|
| `generator_id`         | text    | —    | IIDM generator id                                       |
| `rated_s_mva`          | number  | MVA  | Rated apparent power                                    |
| `min_p_mw`             | number  | MW   | Minimum active power                                    |
| `max_p_mw`             | number  | MW   | Maximum active power                                    |
| `target_p_mw`          | number  | MW   | Active power set point of the base case                 |
| `min_q_mvar`           | number  | Mvar | Lower reactive limit                                    |
| `max_q_mvar`           | number  | Mvar | Upper reactive limit                                    |
| `target_v_pu`          | number  | p.u. | Voltage set point, in p.u. of the nominal voltage       |
| `voltage_regulator_on` | boolean | —    | `True` or `False`: whether the unit regulates voltage   |
| `basis`                | text    | —    | Reference element the values come from                  |

### `network/<variant>_transformer_data.csv`

Optional. Nameplate data of every two-winding transformer, from which the build
derives its series impedance as PowerFactory does: r = P_cu / S_n and
x = √(u_k² − r²) in p.u. of the unit rating, converted to ohms at the nominal voltage
of side 2 and divided by the number of units in parallel. The rating becomes
`rated_s_mva` × `parallel_units`. The build stops if a transformer is missing, unknown
or listed twice, or if the copper losses exceed the short-circuit impedance.

| Column           | Type    | Unit | Description                                 |
|------------------|---------|------|---------------------------------------------|
| `transformer_id` | text    | —    | IIDM two-winding transformer id             |
| `rated_s_mva`    | number  | MVA  | Rating of one unit                          |
| `uk_pct`         | number  | %    | Short-circuit voltage of one unit           |
| `pcu_kw`         | number  | kW   | Copper losses of one unit at rated current  |
| `parallel_units` | integer | —    | Identical units in parallel                 |
| `basis`          | text    | —    | Reference element the values come from      |

### `network/<variant>_load_data.csv`

Optional. Base-case consumption of selected loads. The build stops if a load is unknown
or listed twice. Scenario consumption is set by `scenarios/load_scenarios.csv`.

| Column    | Type   | Unit | Description                             |
|-----------|--------|------|-----------------------------------------|
| `load_id` | text   | —    | IIDM load id                            |
| `p_mw`    | number | MW   | Active power                            |
| `q_mvar`  | number | Mvar | Reactive power                          |
| `basis`   | text   | —    | Reference element the values come from  |

### `network/<variant>_res_units.csv`

Optional. Inverter-based wind and solar units added to the network models as IIDM
generators, idle in the base case and without voltage control. Their rating is
`max_p_mw / power_factor` and their reactive range ± `max_p_mw` · tan(acos
`power_factor`). The build stops if a bus is unknown, an id is repeated or already
used, the energy source is not `WIND` or `SOLAR`, the power is not positive or the
power factor is outside (0, 1].

| Column          | Type   | Unit | Description                                  |
|-----------------|--------|------|----------------------------------------------|
| `generator_id`  | text   | —    | Id of the new generator                      |
| `bus_id`        | text   | —    | Bus-breaker bus of the connection            |
| `energy_source` | text   | —    | `WIND` or `SOLAR`                            |
| `max_p_mw`      | number | MW   | Maximum active power                         |
| `power_factor`  | number | —    | Power factor reachable at full output        |
| `site`          | text   | —    | Illustrative location                        |

The build applies the network inputs in this order: id normalisation and voltage
rescale, the other corrections of `<variant>_corrections.yaml`, generator, transformer
and load data, thermal limits, batteries, renewable units and coordinates.

### `network/<variant>_substation_coordinates.csv`

WGS84 coordinates of every substation, added to the network models as the IIDM
`substationPosition` extension and shipped per bus in `network/bus_coordinates.csv`.
The build stops if a substation is missing, unknown or listed twice, or if a
coordinate is not a number or out of range.

| Column          | Type   | Unit | Description                    |
|-----------------|--------|------|--------------------------------|
| `substation_id` | text   | —    | IIDM substation id             |
| `latitude`      | number | °    | WGS84 latitude                 |
| `longitude`     | number | °    | WGS84 longitude, east positive |

### `scenarios/validation.yaml`

Rules each scenario must satisfy on the base network case. Each top-level key is a
scenario id (`S1`, `S2`, `S3`); every rule is optional.

| Key                       | Type          | Unit | Rule                                                        |
|---------------------------|---------------|------|-------------------------------------------------------------|
| `max_branch_loading_pct`  | number        | %    | No branch loaded above this                                 |
| `voltage_band_pu`         | [number, number] | p.u. | Every bus voltage within the band                        |
| `hvdc_at_max`             | boolean       | —    | Every HVDC line carries its maximum power                   |
| `min_voltage_rise_pu`     | number        | p.u. | Some bus at least this much above its S1 voltage            |
| `min_voltage_drop_pu`     | number        | p.u. | Some bus at least this much below its S1 voltage            |
| `min_overloaded_branches` | integer       | —    | At least this many branches above 100 %                     |

### `network/<variant>_reinforcement.yaml`

The new line of the `reinforced` case.

| Key                    | Type   | Unit | Description                                                 |
|------------------------|--------|------|-------------------------------------------------------------|
| `new_line.id`          | text   | —    | Id of the new line                                          |
| `new_line.parallel_to` | text   | —    | Existing line whose parameters and current limit are copied |
| `new_line.length_km`   | number | km   | Length, for the investment cost                             |

The build stops if the copied line is unknown, the new id is already used or the length
is not positive.

### `network/<variant>_corrections.yaml`

Corrections applied to the source model of a variant; see
[model-changes.md](model-changes.md).

| Key                                        | Type    | Unit | Description                                   |
|--------------------------------------------|---------|------|-----------------------------------------------|
| `voltage_rescale.source_nominal_kv`        | number  | kV   | Nominal voltage of the voltage levels to move |
| `voltage_rescale.target_nominal_kv`        | number  | kV   | Nominal voltage after correction              |
| `voltage_rescale.expected_voltage_levels`  | integer | —    | Number of voltage levels that must match      |
| `tap_ratios.<transformer_id>`              | number  | p.u. | Fixed ratio ρ replacing the tap changer       |
| `parallel_lines[].id`                      | text    | —    | Id of a line added next to an existing one    |
| `parallel_lines[].parallel_to`             | text    | —    | Existing line whose parameters are copied     |
| `hvdc.lines.<id>.nominal_v_kv`             | number  | kV   | Nominal DC voltage                            |
| `hvdc.lines.<id>.r_ohm`                    | number  | Ω    | DC resistance                                 |
| `hvdc.lines.<id>.max_p_mw`                 | number  | MW   | Maximum active power                          |
| `hvdc.converter_stations.<id>.voltage_regulator_on` | boolean | — | Whether the station regulates its AC voltage |
| `hvdc.converter_stations.<id>.target_v_pu`   | number | p.u. | AC voltage set point, if it regulates        |
| `hvdc.converter_stations.<id>.target_q_mvar` | number | Mvar | Reactive set point, if it does not           |
| `hvdc.converter_stations.<id>.min_q_mvar`, `max_q_mvar` | number | Mvar | Reactive limits                |

A transformer listed in `tap_ratios` gets a one-step, non-regulating tap changer at ρ
(side 2 over side 1 voltage at no load, in p.u. of the rated voltages). A parallel line
gets its current limit from `<variant>_thermal_limits.csv` like any other branch.
`hvdc` must cover every HVDC line and converter station of the model.
